---
title: Migrating from Panda CSS
description: Migrate your project from Panda CSS to Bamboo CSS.
---

Bamboo CSS started as a fork of [Panda CSS](https://panda-css.com/), so unlike the other guides in this section this one
is not a rewrite. The styling API is the same: your style objects, recipes, patterns, conditions and tokens carry over
unchanged. What changes is the name of the package they come from.

For most projects this is a find-and-replace of `panda` with `bamboo`, plus a re-run of codegen.

## What stays the same

- `css`, `cva`, `sva`, `cx` and the pattern functions – same names, same signatures. `cva`/`sva` are the exception: they
  emit into the `recipes` cascade layer rather than atomic classes ([below](#recipes-are-named-not-atomic)).
- Recipes, variants, compound variants and default variants. **Slot recipes are the exception** – their output changes
  shape, and it changes silently; see [below](#slot-recipes-scope-their-variants).
- Tokens, semantic tokens, conditions, breakpoints, themes, `staticCss`, cascade layers.
- The config shape, minus five keys. Every key you have in `panda.config.ts` is valid in `bamboo.config.ts` except
  `studio`, `jsxFramework`, `jsxFactory`, `jsxStyleProps` and `syntax`, none of which have an equivalent – delete them.
- The output directory. It still defaults to `styled-system`, so imports like `styled-system/css` do not move.

Because the generated output directory keeps its name and shape, the only imports you have to touch are the ones that
name the tool itself – the config file, the PostCSS plugin, and any direct `@pandacss/*` imports.

## Rename the packages

Every package moves from the `@pandacss` scope to `@bamboocss`. The ones a project normally depends on:

| Panda CSS                | Bamboo CSS                 |
| ------------------------ | -------------------------- |
| `@pandacss/dev`          | `@bamboocss/dev`           |
| `@pandacss/types`        | `@bamboocss/types`         |
| `@pandacss/preset-base`  | `@bamboocss/preset-base`   |
| `@pandacss/preset-panda` | `@bamboocss/preset-bamboo` |
| `@pandacss/postcss`      | `@bamboocss/postcss`       |

The internal packages (`@pandacss/core`, `/node`, `/parser`, `/generator`, `/token-dictionary` and the rest) follow the
same rule if you import them directly.

<Callout type="info">
  The default preset is the one rename that is not a straight scope swap: `@pandacss/preset-panda` becomes
  `@bamboocss/preset-bamboo`. If you never listed presets explicitly, the defaults are applied for you and there is
  nothing to change.
</Callout>

### Rename the config file

`panda.config.ts` becomes `bamboo.config.ts`. Bamboo looks for `bamboo.config.{ts,js,mts,mjs}` and will not pick up a
file under the old name.

Update the import inside it, and the preset names if you listed them:

```ts
// bamboo.config.ts
import { defineConfig } from '@bamboocss/dev'

export default defineConfig({
  presets: ['@bamboocss/preset-base', '@bamboocss/preset-bamboo'],
  include: ['./src/**/*.{js,jsx,ts,tsx}'],
  outdir: 'styled-system',
})
```

### Update the PostCSS config

```js
// postcss.config.cjs
module.exports = {
  plugins: {
    '@bamboocss/dev/postcss': {},
  },
}
```

### Update your scripts

The CLI is `bamboo` (`bamboocss` also works). Every command keeps its name, so `panda codegen` becomes `bamboo codegen`,
`panda cssgen` becomes `bamboo cssgen`, and so on.

```json
{
  "scripts": {
    "prepare": "bamboo codegen"
  }
}
```

### Regenerate the output directory

Delete the existing `styled-system` directory and generate it again, so nothing from the previous install is left
behind:

```bash
rm -rf styled-system
pnpm bamboo codegen
```

</Steps>

## `cx` joins, in both tools

Panda's `cx` joins classnames and so does Bamboo's, so this needs no migration. Two atomic classes for the same property
both end up on the element and the browser picks by stylesheet order.

What differs is the advice about what to do instead. A **recipe** — `cva()` or `sva()`, inline or declared in
`theme.recipes` — lands in the `recipes` layer, so a consumer's `css()` in `utilities` overrides it deterministically.
This is a difference from Panda, where an inline `cva()` emits atomic classes. See
[Merging styles](/docs/concepts/merging-styles).

## Slot recipes scope their variants

The largest behavioural change in the migration, and the one most likely to bite, because nothing about your config has
to change for it to happen.

In Panda, every slot of a slot recipe carries its own variant class:

```html
<div class="checkbox__root checkbox__root--size_md">
  <div class="checkbox__control checkbox__control--size_md">
    <span class="checkbox__label checkbox__label--size_md"></span>
  </div>
</div>
```

In Bamboo, **a slot recipe that declares a slot named `root` is scoped automatically**. The root keeps its variant
class; every other slot's variant styles become `@scope` rules anchored on it, and those slots carry a constant class:

```html
<div class="checkbox__root checkbox__root--size_md">
  <div class="checkbox__control">
    <span class="checkbox__label"></span>
  </div>
</div>
```

```css
@scope (.checkbox__root--size_md) to (.checkbox__root) {
  .checkbox__control {
    width: 10;
  }
}
```

The upside is that a slot arbitrarily deep in a compound component needs nothing delivered to it — no context, no
provider, no wrapper. See [Slot recipes](/docs/concepts/slot-recipes#only-the-root-takes-variants).

### What this means for a migrating app

- **Selectors you wrote against a non-root slot's variant class no longer match.** `.checkbox__control--size_md` is not
  emitted any more. Anything targeting one — a test, a Playwright locator, a global stylesheet, a snapshot — needs
  updating.
- **The browser floor moves.** `@scope` needs Chrome 118, Firefox 146, Safari 17.4, and there is no polyfill. Of those
  it is Firefox that binds: Bamboo's [browser baseline](/docs/overview/browser-support) is Chrome ≥ 123, Safari ≥ 17.5
  and Firefox ≥ 146, with the first two set by `light-dark()` rather than by `@scope`. It is not something a recipe can
  opt out of — `scopeRoots: []` stops the scoping, but the baseline is what Bamboo supports either way.
- **A portaled slot needs a second anchor.** A `<Select>` whose listbox renders through a portal is outside the root's
  subtree, so a scope opened at the root cannot reach it — its base styles still apply, so it renders _nearly_ right.
  Name both enclosing slots:

  ```ts
  scopeRoots: ['root', 'positioner']
  ```

  An anchor is callable, so the variant still has to reach the positioner — that is one context per portaled component,
  against one per slot in Panda. See
  [Components that span a portal](/docs/concepts/slot-recipes#components-that-span-a-portal).

If you would rather migrate without any of this and revisit it later, `scopeRoots: []` on each slot recipe reproduces
Panda's output exactly.

## Recipes are named, not atomic

`cva()` and `sva()` emit one class per variant, into the `recipes` cascade layer:

```js
cva({ base: { padding: '4' }, variants: { size: { sm: { fontSize: 'sm' } } } })
// panda:  'p_4'                                  in @layer utilities
// bamboo: 'cva_a1b2c3' + 'cva_a1b2c3--size_sm'   in @layer recipes
```

The class name is derived from the config — set `className: 'button'` for a readable one. The practical difference is
that a component written with `cva` is reliably overridable: its styles are in a lower layer than a consumer's `css()`,
so the consumer wins by cascade rather than by stylesheet order. In Panda an inline `cva` is atomic and sits in the same
layer as its consumer.

Compound variants change shape with it. Panda joins atomic classes for them at runtime; Bamboo emits a compound selector
— `.button--size_sm.button--tone_a` — so the whole recipe sits in one layer and the runtime computes nothing. No class
is added for a compound variant, because the rule matches on the variant classes the element already has.

## Things that are easy to miss

- **`PANDA_DEBUG`** is now `BAMBOO_DEBUG`. See [Debugging](/docs/guides/debugging).
- **There is no JSX factory.** `styled.div`, `panda.div`, `styled('button', recipe)`, `createStyleContext` and
  `splitCssProps` have no equivalent, and `styled-system/jsx` is not generated at all. Style props become a `css()`
  call, and a recipe component becomes an ordinary component that calls the recipe:

  ```tsx
  // panda
  const Button = styled('button', buttonRecipe)
  <Button size="sm" />

  // bamboo
  const Button = (props: ButtonProps) => {
    const [variantProps, rest] = buttonRecipe.splitVariantProps(props)
    return <button {...rest} className={cx(buttonRecipe(variantProps), props.className)} />
  }
  ```

  `jsxFramework`, `jsxFactory` and `jsxStyleProps` are gone from the config with it — delete them.

- **There are no JSX pattern components.** `<Stack>`, `<Box>`, `<HStack>` and the rest are not generated, and
  `styled-system/jsx` does not exist to import them from. The pattern **functions** are unchanged and are what those
  components wrapped, so the rewrite is mechanical:

  ```tsx
  // panda
  import { Stack } from '../styled-system/jsx'
  ;<Stack gap="4" align="center">
    {children}
  </Stack>

  // bamboo
  import { stack } from '../styled-system/patterns'
  ;<div className={stack({ gap: '4', align: 'center' })}>{children}</div>
  ```

- **There is no template literal syntax.** ``css`color: red` ``, and the template form of `cva`, `sva` and the patterns,
  are not supported. Write the object form:

  ```tsx
  // panda
  const heading = css`
    font-size: 24px;
    font-weight: bold;
  `

  // bamboo
  const heading = css({ fontSize: '24px', fontWeight: 'bold' })
  ```

  The `syntax` config key is gone with it — both values — so delete it if you set it either way.

- **The ESLint plugin** is `@bamboocss/eslint-plugin`.
- **Editor and CI caches.** The TypeScript server holds on to the old `styled-system` types; restart it after
  regenerating.
- **`.gitignore`.** If you generate `styled-system` in CI rather than committing it, the entry does not change, since
  the directory name is the same.

## Worth a look once you have migrated

These are documented in full elsewhere, and none of them are required to get a migrated project building:

- [Source transformation](/docs/guides/source-transformation) – `@bamboocss/vite` folds statically-resolvable `css()`
  and pattern calls into plain class strings at build time, so they cost nothing at runtime.
- [`pruneUnusedTokens`](/docs/references/config#pruneunusedtokens) – drops token CSS variables nothing can reach, which
  is usually the largest single saving in render-blocking CSS. On by default.
- [`prunePreflight`](/docs/references/config#prunepreflight) – drops the parts of the reset that style elements your
  source never renders, which is most of what is left once the tokens have gone. Off by default, and the one pruning
  option that cannot be proven from the build.
- [Spec files](/docs/theming/spec) – generate a machine-readable description of your design system.
- [MCP server](/docs/ai/mcp-server) and [llms.txt](/docs/ai/llms-txt) – expose your design system to AI tooling.
